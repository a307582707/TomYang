# 架构决策：为什么我们暂不上 Istio，也不全量 Helm

> 题材类型：为什么我们不这样用  
> 适合标题：`我们评估了 Istio 三个月，最后只上了 Gateway API + 自研流量插件`  
> 目标：展示「能说清取舍」，而不是「会装很多组件」

## 0. 决策摘要（给忙人看）

| 议题 | 结论 | 一句话原因 |
|------|------|------------|
| 全量 Istio | **不做**（至少 12 个月内） | 复杂度与故障半径超过收益；现有痛点可用更轻方案覆盖 80% |
| 全量 Helm 统一交付 | **不做** | 多环境差异与权限模型不匹配；GitOps + Kustomize 更可控 |
| Gateway API | **做** | 南北向流量标准演进方向清晰，替代部分 Ingress 注解地狱 |
| 服务网格（部分） | **可选试点** | 仅支付链路 mTLS 试点，不用全网格

下面两篇都是「ADR 风格」完整样例，可直接贴 Wiki。

# ADR-001：暂缓全量引入 Istio

## 状态

**Rejected for GA / Deferred**（2025-Q3 评审）  
复审时间：2026-Q2 或「跨集群零信任」立项时。

## 背景

业务提出诉求：

1. 服务间强制 mTLS  
2. 按 Header 做金丝雀  
3. 统一观测（黄金指标自动出）  
4. 多集群流量调度

平台组收到的隐含压力是：「别的公司都上 service mesh 了」。

## 方案对比

| 维度 | 全量 Istio | Cilium + Gateway API + 自研插件 | Nginx Ingress + 应用 SDK |
|------|------------|----------------------------------|---------------------------|
| mTLS | 强 | Cilium WireGuard / 局部 mTLS | 弱，需应用改造 |
| 金丝雀 | 强（VirtualService） | Gateway/HTTPRoute + Flagger 可覆盖 | 注解能力碎片化 |
| 性能开销 | sidecar +1 hop，P99 常见 +2~8ms | 无 sidecar 或少 sidecar | 低 |
| 故障半径 | 控制面/数据面均可全局影响 | 局部 | 局部 |
| 人员成本 | 需专职 mesh oncall | 现有网络组可吸收 | 最低 |
| 落地周期 | 6~9 个月全量 | 1~2 个季度 | 已具备 |

### 我们做过的验证（细节很重要）

**压测环境**：200 服务，QPS 2w，payload 2KB。

| 指标 | 基线（无 mesh） | Istio sidecar | 差值 |
|------|-----------------|---------------|------|
| P99 延迟 | 42ms | 51ms | +9ms |
| 单节点 CPU | 61% | 74% | +13pt |
| 启动耗时（冷启） | 3.1s | 6.8s（含 proxy ready） | +3.7s |
| 一次错误配置影响面 | 单服务 | 曾误配导致 40+ 服务 503（演练） | 高 |

演练事故（值得写进文章）：

> 测试环境把 `DestinationRule` 的 outlierDetection 阈值设过激，支付下游抖动时被「熔断」成雪崩。  
> 复盘结论：mesh 把「局部故障」放大成「策略故障」的风险真实存在。

## 决策

1. **12 个月内不全量上 Istio**。  
2. 用 **Gateway API** 承接南北向灰度。  
3. 东西向 mTLS：支付命名空间用 **Cilium 策略 / 局部方案** 试点。  
4. 观测：继续完善统一 tracing + RED 指标，不靠 mesh 自动生成。

## 后果（Consequences）

**正面**

- 避免引入第二套控制面 oncall  
- 发布链路不额外绑死 sidecar 注入  

**负面 / 债务**

- 细粒度 L7 治理能力弱于 Istio  
- 多集群流量调度仍需后续专项  
- 需要抵制「别人都上了」的组织压力（靠本文 ADR）

## 复审触发条件

出现任一条则重开评估：

- 合规强制「全站服务间 mTLS」且期限 < 6 个月  
- 跨集群调用占比 > 30% 且故障频发  
- 平台人员编制允许专职 mesh 小组（≥2 人 oncall）

# ADR-002：不全量用 Helm 作为唯一交付方式

## 状态

**Accepted**：核心平台组件可用 Helm；业务工作负载默认 **GitOps + Kustomize/纯 YAML**。

## 背景

曾有提案：「所有服务必须 Helm chart，版本用 Chart.yaml 管。」

现实问题：

1. 业务环境差异大（机房 A/B、特性开关、副本与亲和性）  
2. Helm release 密钥与 values 权限难做细粒度  
3. `helm upgrade` 与 GitOps 双写，容易漂

## 典型翻车案例（写进 Wiki 很加分）

**事件**：某次 `values-prod.yaml` 中误把 `replicas: 2` 提交进公共 chart 默认值，`helm upgrade --reuse-values` 在另一团队执行时覆盖了他们本地未入库的紧急扩容（replicas=20），导致大促前容量回退。

根因不是 Helm「不好」，而是：

- **状态真相**有两份：Git 与 Helm release secret  
- `--reuse-values` 掩盖了漂移  

## 决策规则（可执行）

| 类型 | 交付方式 | 原因 |
|------|----------|------|
| 第三方组件（ingress、cert-manager、监控） | Helm（锁定 chart 版本 + 镜像） | 上游以 chart 发布 |
| 内部业务 Deployment/Service/Config | GitOps 渲染产物 | 审计、评审、回滚清晰 |
| 一次性 Job / CR | 清单入库 | 避免 chart 抽象过度 |

## 规范片段（可直接落地）

```text
允许：helm upgrade cert-manager -n platform -f values/prod.yaml --version 1.14.x
禁止：业务服务把环境差异全塞进一个 chart 的 if/else
要求：任何生产变更必须能在 Git 找到对应 commit；Helm 仅用于「组件安装器」
```

## 一句话对外表述

> 我们不是反 Helm，而是反对「用模板语言掩盖环境真相」。  
> 交付系统的核心是**可审计的期望状态**，不是包管理器本身。

## 写作技巧：如何让读者觉得你是大牛

1. 用表格对比，不要只用形容词「太重」「不好维护」。  
2. 写至少一次**验证数据**或**演练事故**。  
3. 给出**复审条件**，显得你不是情绪化拒绝新技术。  
4. 结尾落到「现在怎么做」，避免变成吐槽贴。
