# 一次差点全站回滚的发布：应用没坏，坏的是迁移顺序

## 0. 案例摘要

| 项 | 内容 |
|----|------|
| 变更 | `billing-api` v2.14.0：账单字段新增 `tax_region`；含 DB migration |
| 策略 | 金丝雀 5% → 25% → 100%（Flagger / Argo Rollouts 同类） |
| 假象 | 金丝雀成功指标全绿（HTTP 成功率、P99） |
| 真相 | migration 在全量前执行；旧版本写库路径触发锁升级，主库 CPU 100% |
| 结果 | 紧急停止放量 + 限流；未全站回滚应用，但回滚了迁移策略认知 |

---

## 1. 当时的发布流水线（画出「关卡」）

```text
PR 合并
  → 构建镜像 & 签名
  → 部署到 staging + 自动化回归
  → 人工审批（生产）
  → 执行 DB migration（！！！问题点）
  → 金丝雀 5%
  → 自动分析（成功则继续）
  → 25% → 100%
  → 观察窗 30min
```

**缺陷**：把 **DB schema 变更** 和 **应用放量** 绑在一个「成功」里，但健康检查只看应用 HTTP。

---

## 2. 时间线

| 时间 | 事件 |
|------|------|
| 10:02 | migration 执行：`ALTER TABLE bills ADD COLUMN tax_region ...`，大表 1.2 亿行 |
| 10:08 | migration「成功」；金丝雀 5% 启动 |
| 10:10 | 金丝雀指标：成功率 99.95%，P99 210ms（基线 200ms）→ **判定通过** |
| 10:12 | 放量 25% |
| 10:15 | 主库 CPU 爬升到 85%，锁等待增加 |
| 10:18 | 老版本 Pod（仍 75% 流量）大量出现 `lock wait timeout` |
| 10:19 | 告警：账单写入失败率 7% |
| 10:20 | 发布负责人 **暂停 Rollout**，网关限流 |
| 10:27 | 杀掉长事务，取消后续 DDL；应用保持 canary 暂停 |
| 10:45 | 库恢复；决定：本次发布中止，按扩展迁移规范重做 |

## 3. 为什么金丝雀会「误判健康」

| 检查项 | 金丝雀看了吗 | 是否足够 |
|--------|--------------|----------|
| HTTP 5xx | 看了 | 不足：业务错误码当 200 |
| P99 延迟 | 看了 | 不足：新版本本身不慢 |
| 下游 DB | **没看** | 致命 |
| 旧版本错误率 | **没看** | 致命（兼容性问题只打老版本） |
| 迁移锁时长 | **没看** | 致命 |

**根因模型**：

```text
新版本读新列：OK
旧版本写同一行：触发更重的行锁 / 隐式转换
流量大部分仍在旧版本 → 金丝雀「自己」很健康，整体在恶化
```

这是经典的 **「金丝雀视角偏差」**。

---

## 4. 发布分层规范

### 4.1 数据库变更与应用变更解耦

采用 expand / contract：

1. **Expand**：加可空列 / 新表，不删不改旧列；迁移可长时间 online  
2. **双写或旁路填充**：后台 job 回填  
3. **切换读**：应用新版本读新列  
4. **Contract**：确认无旧代码依赖后删旧列  

禁止：

- 在放量流水线里跑超过 N 秒的 DDL  
- 不带 `ONLINE`/`CONCURRENTLY` 的大表改写（按引擎而定）

### 4.2 金丝雀成功判定必须包含「存量」

伪策略：

```yaml
analysis:
  metrics:
    - name: canary-success-rate
      threshold: 99.9
    - name: stable-success-rate   # 旧版本
      threshold: 99.9
    - name: db-cpu
      threshold: 70
    - name: db-lock-waits
      threshold: <基线*1.5>
  interval: 1m
  maxWeight: 25   # 未过 DB 门禁前不超过 25%
```

### 4.3 回滚分级

| 级别 | 触发 | 动作 | RTO 目标 |
|------|------|------|----------|
| L1 | 仅新版本指标差 | 回滚 Deployment/Rollout | ≤ 3 min |
| L2 | 新旧都差或 DB 伤 | 停放量 + 限流 + 保核心写 | ≤ 5 min |
| L3 | schema 不兼容已全量 | 启动兼容补丁版本（forward fix）优先于 down migration | 视数据 |

原则：**数据回滚极危险，优先向前修。**

---

## 5. 发布检查单（事后固化）

发布前：

- [ ] 是否有 DDL？大表？预估锁时长？  
- [ ] 是否 expand/contract？旧版本是否兼容新 schema？  
- [ ] 金丝雀是否监控 stable + DB？  
- [ ] 特性开关能否秒关？  
- [ ] 回滚演练记录（staging）是否在 30 天内？

发布中：

- [ ] 看新版本、旧版本、依赖三条曲线  
- [ ] DB 有专人同屏  

发布后：

- [ ] 观察窗内禁止接第二个 DDL  
- [ ] 写发布复盘（即使成功也记「险情」）

## 6. 另一个短例：配置热更新导致的「幽灵回滚」

**现象**：回滚了镜像，故障仍在。  
**原因**：ConfigMap 被另一流水线写成新值；Pod 没重建时可能仍用旧配置，重建后反而吃到「新配置 + 旧镜像」的最差组合。  

**规范**：应用配置与镜像版本 **同一 Git commit 原子发布**；回滚用同一个 commit revert，而不是只改 image tag。

---

## 7. 结论

金丝雀验证的是新版本自身是否健康；生产要的是整条链路是否健康。数据库变更如果不能独立回滚，就不要和应用放量绑在同一个按钮里。
